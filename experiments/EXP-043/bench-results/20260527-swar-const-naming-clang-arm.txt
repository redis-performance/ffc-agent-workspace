# Change: ffc_loop_parse_if_eight_digits in parse.h
#   Declared SWAR check/scale constants as named const variables before the while loop:
#     const uint64_t swar_check = UINT64_C(0x4646464646464646);
#     const uint64_t swar_mask  = UINT64_C(0x000000FF000000FF);
#     const uint64_t swar_mul1  = UINT64_C(0x000F424000000064);
#     const uint64_t swar_mul2  = UINT64_C(0x0000271000000001);
#   These were passed into ffc_is_made_of_eight_digits_fast and
#   ffc_parse_eight_digits_unrolled_swar as explicit arguments.
#
# Analysis:
# The hypothesis was that Clang rematerializes ~11 SWAR constants inside the loop
# body each iteration (vs. GCC which hoists them to callee-saved registers x22/x23).
# Explicitly naming them as const variables before the loop was expected to trigger
# Clang's LICM pass to hoist them into registers.
#
# Result: i/f unchanged at 245.02 — identical instruction count, hypothesis disproved.
# Clang generates the same code regardless of source-level naming. The root cause is
# register pressure: the large inlined findmax_ffc context uses all available
# caller-saved registers, so Clang cannot keep additional values live across the
# loop back-edge without spilling. GCC's different register allocation strategy
# (larger function size, different spill decisions) naturally keeps constants live.
# This is a structural compiler difference not addressable at the source level without
# restructuring the function boundaries.
#
# The random regression (-2.6% c/f) with unchanged i/f is a code layout/alignment
# artifact from the slightly different source structure.
#
# Decision: REJECTED
