### Brief: ffc-gcc-random-gap

**ffc GCC/x86 random deficit — disassembly-level root cause**

**Method.** perf is blocked on this box (paranoid=4, no sudo), so I wrote a ptrace single-step tracer (`scratchpad/tracer.c`) that breakpoints the prebuilt binaries' hot functions and histograms 400k executed RIPs against `objdump`. Gap confirmed locally first (gcc random, core 3): fastfloat 1676–2012 MB/s vs ffc 1613–1951, ffc consistently −2…−7%.

**Instruction counts (exact, traced).** Random input shape is `d.dddddddddddddddde-dd` (%.17g). Per float:

| | gcc | clang |
|---|---|---|
| ffc | **257.1 i/f** | 281.1 i/f |
| fast_float | **229.0 i/f** | 316.0 i/f |

gcc/ff = 229 i/f matches the gnr1 fleet counter exactly; ffc +28 i/f under gcc, but −35 under clang — a pure GCC-codegen inversion. Branches are equal (ffc 46/f vs ff 45/f under gcc), so this is instruction volume, not prediction.

**Where the +28 lives (per-stage diff, gcc):** Eisel-Lemire **+17.9** (57.0 vs 39.0), dot-detect trampoline **+7.0**, round/assemble **+5.0**, exp-parse +4.0, tail-digit checks +3.0, span bookkeeping +3.0; ffc wins back: no rounds_to_nearest probe **−6.0** (ff pays a runtime fmin vaddss/vsubss/vucomiss probe; ffc has `-DFFC_ROUNDS_TO_NEAREST`), front block −4.0, SWAR8 loop −4.0 (GCC rematerializes two `movabs` masks per iteration in ff's loop but hoists them in ffc's).

**Root cause: struct spill traffic.** Stack ops per float: gcc/ffc **17 stores + 3 loads**; gcc/ff 3+2; clang/ffc 7+4. In ffc's EL region (0x100fc–0x10210) 16 of 57 instructions are `mov [rsp+0x38..0x7c]` stores/reloads of the 72-byte `ffc_parsed` plus `ffc_adjusted_mantissa` fields — fast_float's EL keeps everything in registers (1 store). Cause in source (`ffc/src/ffc.h` ~line 335): `am = ffc_digit_comp(pns, am, vk)` passes `pns` **by value to a non-inlined cold function** (`ffc_digit_comp.isra.0` exists as a standalone symbol). The address/value escape blocks GCC's SRA, and GCC (unlike clang) won't sink the dead stores into the cold branch — so every hot-path float pays full struct materialization. The +7 dot-detect block (0x10310) is the same disease: it stores span fields `[rsp+0x18]=1` (int_part_len), `[rsp+0x8]=rbp` (part pointer) before rejoining; `too_many_digits` is stored and reloaded at 0x10904 (+5 assemble). fast_float avoids all of this since pr386 span-elision (our EXP-059): its hot path materializes no spans and its slow-path call re-parses.

**Fix directions (target: ffc), ranked by expected gain:**
1. **De-escape `pns` at the digit_comp boundary** — call a `noinline,cold` shim taking only scalars (mantissa, exponent, negative, first/last pointers) that rebuilds `ffc_parsed` inside; lets GCC fully SRA `pns`. Expected ~14–16 i/f (≈6%) on gcc random, clang-neutral.
2. **Span elision (mirror EXP-059 into ffc)** — drop `int_part_*`/`fraction_part_*` from the hot path; re-derive on the rare digit_comp path by re-scanning. Removes the 0x10310 span stores and shrinks `ffc_parsed` to SRA-friendly size. ~5–7 i/f, also helps canada/mesh slightly.
3. **Keep `too_many_digits` in a register-friendly local** (separate bool, not a struct field read after EL) — kills the store+reload+branch chain at 0x10904. ~3–4 i/f.
4. **Inline the `.`-after-first-digit check into the int-scan exit** (avoid the 0x10310→0x10748→0xff56 jump chain). ~2–3 i/f.
5. Cross-pollinate the other way (target fast_float): hoist the two SWAR mask `movabs` out of its 8-digit loop (−4 i/f) and honor a compile-time FE-rounding define to skip the 6 i/f runtime probe.

### Brief: fastfloat-canada-mesh-gap

All evidence gathered. Writing the brief.

---

**TL;DR: ffc wins canada/mesh on x86 because its fraction-tail is straight-line SWAR (4-digit step + unrolled ≤3-digit chain) where GCC fast_float runs a serial byte-loop, and because ffc short-circuits pure integers past the Clinger rounding-mode probe — both are portable restructures fast_float can adopt, and un-gating the existing 4-digit step from clang-only is a one-line +11% canada win on GCC.**

**Evidence**

*Data shapes:* canada = 2-3-digit int + 14/15-digit fraction (86.6k×15, 21.7k×14) → Clinger always fails (mantissa > 2^53), Eisel-Lemire path; after one 8-digit SWAR the fraction leaves 6-7 digits. mesh = 55% short pure integers + 45% floats with 11-13-digit fractions (3-5 digits left after 8-SWAR).

*Disassembly (gcc 13.3 harness binary):* fast_float's fraction remainder runs a byte-at-a-time loop (`findmax_fastfloat+0x410`: movsbl/sub/cmp/ja + 2×lea + cmp/jne = ~8 instr, 2 branches, serial `i=10i+d` dep chain per digit, trip count alternating 6↔7 → data-dependent exit mispredicts). The 4-digit SWAR constant `0x640001` exists in the ffc binary but is **absent** from fast_float's — upstream gates the 4-digit follow-up to `#if defined(__clang__)`. ffc consumes the same remainder as one 4-digit SWAR + ≤3 straight-line digits, zero back-edges. This exactly matches the gnr1 signature: near-equal i/f (225 vs 233) but 36.4 vs 41.8 c/f — latency chains + mispredicts, not instruction count. For mesh, ffc additionally has an integer express path in dispatch (`exponent==0 && mantissa≤MAX_FAST_PATH` → `value=T(m)` directly), skipping the `rounds_to_nearest()` volatile-load/FP-compare probe, the pow10 table load and the fmul that fast_float pays on every one of mesh's 55% integers.

*Scratch validation* (standalone harness, gcc 13.3 -O3, pinned, 3 stable runs; perf blocked, paranoid=4): un-gating the 4-digit step (A1): canada **+11.2%**, mesh **+3.7%**, random[0,1] **+3.0%** — all-win; the historical gcc-regression rationale for the gate does not reproduce. Unrolled 1-3 chain replacing the tail while-loop (A2, alone): random **+14%**, canada +3.4%, mesh +2.1%. A1+A2 combined: canada +15% but random −6…−20% (GCC layout/inlining fragility — the parts win separately, so land stepwise). Integer express at dispatch level (B): mesh **+5%**, but canada −2.5% consistently (extra never-taken branch placed too early).

**Ranked candidate directions (all target fast_float, portable/upstreamable)**

1. **Delete the `__clang__` gate on the 4-digit SWAR follow-up** in `loop_parse_if_eight_digits(char)` (ascii_number.h ~l.274). One-line diff, +11% canada / +3.7% mesh / +3% random on GCC locally, no-op on clang. Highest confidence; PR-ready after harness validation.
2. **Unroll the fraction 1-3-digit tail** (ascii_number.h ~l.435) into ffc's if-chain (no back-edge). +14% random alone on GCC — but must be benchmarked *with and without* #1 per compiler; accept whichever combination shape avoids the GCC layout regression (chain-without-while variant tested: canada +14.8%, random still −6%).
3. **Integer express path inside `clinger_fast_path_impl`**: hoist `exponent==0` (result `T(mantissa)` is exact in *any* rounding mode, so it may legally bypass `rounds_to_nearest()` and the pow10 multiply) after the existing exponent-range check rather than as a new dispatch pre-check — captures mesh's +5% without B's −2.5% canada branch cost. Fits history: naive pre-checks regress, structural re-ordering wins.
4. **Cross-pollination flag for ffc**: A2's +14% random on GCC shows the tail chain is not why ffc trails GCC random; ffc's ~40 extra i/f there needs separate profiling (suspect: always-materialized span stores / struct width).
